The problem

Bias hides in the language of the debrief.

“He's not really a culture fit.”   “She lacks executive presence.”   “Great energy — maybe not enough gravitas.”

No one here is a villain — we're just wired to favour people who remind us of ourselves, often before we're even aware of it.

One debrief looks fine. The pattern across ten is invisible — and no one ever shows the manager their own.

Where this started for me: I'd been reading about why interviewers tend to favour candidates who remind them of themselves — even when they're actively trying not to — and it stuck with me. What hooked me wasn't the fairness angle, it was the psychology: our brains run shortcuts below the level of intention, and good intentions don't reach them. So bias in hiring is rarely a slur — it's coded, plausible language that shifts the bar. "Culture fit," "presence," "energy." Each note passes review; the signal only shows up in aggregate, and nobody ever reflects it back to the manager. That gap is the opportunity.

The insight

Audit tools police. FairHire reflects.

The real question isn’t “were you fair?” — everyone says yes. It’s: make the invisible patterns visible, without making the manager feel watched.

So FairHire is a private review tool for the decision-maker — the way a writer uses a spell-checker. You see your patterns first; no one is looking over your shoulder.

Get that trust wrong, and nothing else matters.

This is how I re-read the brief. The brief asks how tech can help managers spot bias; the more useful framing is "make invisible things visible without making the manager feel watched." A compliance tool that sits in judgment gets routed around — people write blander notes and the bias just goes unrecorded, which is worse. So I flipped it: the manager is the first and primary audience for their own data. A mirror they choose to look into. That reframe drives every privacy decision that follows — the next slide.

The trust contract

Who sees what.

The manager

Sees only their own interviews and their own patterns. Nothing about anyone else's.

HR

Sees only anonymised, org-level aggregates — never an individual manager's data or a candidate's excerpt.

Not a policy. Enforced at the database layer — and proven by tests.

This boundary is the trust contract. A manager never sees a colleague's interviews. HR gets the org picture but can't drill into a person. The important part — and I'll show how — this isn't a promise in a privacy policy or an if- statement in my code that I could get wrong. It's enforced by Postgres itself, and I wrote adversarial tests that try to break it and confirm they can't.

How it works

A hybrid engine: rules + LLM

A fast rulebook for the obvious cases; an AI for the judgment calls — each cross-checking the other.

  • Rules are explainable, free and always on. The LLM catches nuance the rules miss.
  • Run both and merge — not one or the other. If the LLM is unavailable, it degrades to rules-only, never to nothing.
  • Mode-aware: a different rule set and prompt for hiring vs promotion.
I didn't want to bet the whole thing on an LLM — it's non-deterministic and can hallucinate — but pure rules miss anything they weren't written for. So I run both on every transcript and merge the results, with the higher-confidence flag winning on overlaps. The rules give a guaranteed floor and full explainability; the LLM adds nuance. And if OpenAI is down, the run quietly falls back to rules- only rather than failing.

Why the trust contract holds

Privacy by construction.

create function hr_flag_summary()
  returns table (flag_type text, count int, dismissed int)  -- no manager_id. no excerpt.
  security definer                                       -- runs as owner; org taken from the caller's identity
  • HR's data has no column that could leak an individual — there's no manager_id or excerpt in the return type at all.
  • Exposure isn't filtered out — it's structurally unrepresentable.
  • Every manager query is scoped by Postgres row-level security across 11 tables; adversarial cross-tenant tests prove one manager can't read another's rows.

In plain terms: HR’s report is printed on a form with no space to write a name — so a name can never appear, even by accident.

This is the slide I'm proudest of. Naive approach: give HR a broad read and filter columns in the API — but one wrong query leaks a name. Instead, HR reads through a database function whose return type only has aggregate columns. There is literally no field in the result that identifies a manager or shows a quote — so it can't leak, even if my API code had a bug. And the manager side is locked down by Postgres row-level security, which I verify with tests that literally try to read across tenants and assert they get nothing. Privacy is a property of the schema, not a promise in my code.

The balance between the two.

  • Scored per flag type against a labelled ground-truth set — run any time with npm run eval.
  • Plus a fairness breakdown by race & gender, and honest, documented limitations.
A bias tool that is itself biased or noisy is worse than nothing, so I built an eval harness. It re-runs the engine against a labelled set and reports precision, recall and F1 per flag type — no single vanity accuracy number. It also breaks the results down by demographic so I can check the detector isn't itself skewed, and I documented where it's weak. If you want live numbers, run `npm run eval`.

How I framed it

Four tensions any honest solution must face.

  • Bias is invisible in the moment. Ask “were you fair?” and you'll always hear yes — so the tool surfaces what you couldn't see, it doesn't interrogate.
  • Bias lives in patterns, not single calls. Any one debrief looks reasonable — so the Mirror aggregates across all your decisions.
  • The same data that helps can surveil. Feel watched and you game it or quit — so isolation is enforced in the database; HR sees only anonymised aggregates.
  • “Biased language” is subjective. Over-flag and you're ignored; under-flag and you catch nothing — so calibration is conservative by design.

One principle underneath all four: augment the manager’s judgement — never replace it.

This is the analytical spine — the four tensions I laid out in my original proposal, and each one drove a concrete engineering choice you've just seen. Invisible-in-the-moment is why the product reflects rather than asks. Patterns- not-single-calls is why the Mirror exists. The-data-that-helps-can-surveil is why isolation lives in Postgres, not my API code. And subjective-language is why the detector is tuned to stay quiet rather than cry wolf. The one line under all of it: augment judgement, never replace it — the tool never scores or auto-rejects anyone.

Phase 2

Where it goes next.

  • HRIS integration — pull candidates & decisions from the systems teams already use.
  • Live transcription — flag language during the debrief, not after.
  • Nudge thresholds tuned on real signal — today's are deliberately cautious placeholders.
  • Fine-tuning on labelled debriefs to lift recall on the subtler categories.
Where I'd take it: connect to the HR systems so it's zero-effort to adopt; move from post-hoc to live so the nudge lands in the moment; and tune the nudge thresholds on real organisational data — right now they're intentionally cautious placeholders. Longer term, fine-tune the model on labelled debriefs to catch the subtler patterns.
